# Hot-path profiler (Run 15)

## Резюме

В крейт ticklog добавлен встроенный **hot-path профилировщик** (feature
`hotpath-profiler`, модуль `src/hotpath.rs`): каждая `dispatch` на продюсерской
ните записывает rdtsc-дельты по пяти стадиям в thread-local массив, harness
читает счётчики `take()` и печатает breakdown в stderr. Запущен бенч под
профайлером (ring 8 MiB, samples=1000, threads 1/2/4/8/16) на обеих
платформах и найден ботлнек каждого бэкенда.

Прибор измерителя сам добавляет ~130–210 ns на вызов (2× rdtsc + TLS per
стадия), поэтому **абсолютные** total'ы завышены; относительное распределение
стадий внутри конфига при нулевых дропах (t8/t16) информативно.

## Стадии (lane)

| Lane | Что меряет |
|---|---|
| `total`   | весь `dispatch` (вход в with_thread_buf → выход) |
| `ts`      | `timestamp::raw_timestamp()` |
| `reserve` | reserve с политикой (fast-tail-cache резерв / handoff сегмента) |
| `assemble`| запись записи в слот (header + args) |
| `publish` | публикация слота дренажу (или commit для rtrb) |
| `cold`    | подтверждение tail на холодном пути (кэш-мисс) |

### Выводы

1. **ticklog-quill и ticklog-nanolog** — без явного ботлнека: все стадии на
   уровне шума измерителя (~17 ns) на любой ширине. Уже сбалансированы.
2. **custom-кольцо** — ботлнек в **assemble** (запись 25-байтового заголовка +
   args в выделенный слот): 76→136 ns на WSL при росте потоков. При этом резерв
   дёшев (fast-tail-cache работает, ~16–20 ns), публикация тоже (~17–23 ns).
   Дорогой encode — запись в кольцо через `record::assemble` одной нитью;
   основной кандидат на оптимизацию.
3. **rtrb** — ботлнек в **publish** (commit в кольцо): 101→257 ns при t16 на
   WSL. Commit дорогой (мультикас-запись + fence), резерв дёшев (17 ns).
   Это объясняет то, что в Run 14 rtrb был при t8+ быстрее всех по throughput
   (поточный размер) но его p50 растёт с threads из-за commit.
4. **ts** — константа ~32–46 ns у всех: это стоимость `raw_timestamp()` (rdtsc);
   стабильна на любой ширине, не является точкой оптимизации.

### Артефакт измерителя (важно при интерпретации)

- Профайлер добавляет ~130–210 ns на вызов; на t1–t4 (низкая ширина) ring
  custom/rtrb **переполняется** (дропы 87–99 %), т.к. продюсер замедлён
  прибором, а дренаж не испинян на ядро (`backend_core` не задан). На t8+ у
  всех 0 дропов — цифры чисты.
- Итоговая задержка p50 профильных бинарей (137–243 ns) — НЕ показатель
  реальности, сравнивать со штатными прогонами (15–65 ns) нельзя. Профайлер
  нужен для относительного распределения стадий, не для абсолютных чисел.

## Файлы

- `src/hotpath.rs` — новый модуль профилировщика (TLS-счётчики, `take()`).
- `src/lib.rs` — `pub mod hotpath`, re-export в `__private`.
- `src/macros.rs` — хуки в `dispatch` (оба варианта: fifo и non-fifo).
- `src/ring.rs` — хук `L_COLD_CONFIRM` в `try_ensure_capacity`.
- `Cargo.toml` (root + harness) — feature `hotpath-profiler`.
- `cross-lang-bench/rust/ticklog/src/main.rs` — сборка `take()` + stderr-отчёт.
- `build_{win,wsl}_prof.*`, `run_{win,wsl}_prof.*` — скрипты сборки/прогона.
- `results_quill/{wsl,windows}_ticklog_*_prof.{json,log}` — сырые данные.
