# ticklog — custom-ring **Drop** sweep: Windows vs WSL

Оба прогона использует **один и тот же** харнесс (`cross-lang-bench/rust/ticklog`,
`[[bin]] ticklog-cross-lang-harness`), собранный **с одной и той же фичей**
`--features policy-drop` → `policy() == Backpressure::Drop`
(main.rs:40–41), и **тем же самым кастомным кольцом** (SPSC ring, `DEFAULT_RING_SIZE`
= 1 MiB — флаг `--ring-capacity` нигде не передан, поэтому обе платформы
используют дефолт 1 MiB, байт-в-байт). Разница только в одной графе — `os`:

| | Windows (os=windows) | WSL (os=linux) |
|---|---|---|
| clock | RDTSC | RDTSC (x86_64 ELF) |
| ns_per_tick | 0.313097 | 0.313097 (калибр. WSL2, тот же физ. CPU) |
| sink | NullSink | NullSink |
| кандидат | ticklog (custom-ring) | ticklog (custom-ring) |
| threads | 1,2,4,8,16 | 1,2,4,8,16 |
| batch | 1000 | 1000 |
| total | 10_000_000 | 10_000_000 |

## Вывод

WSL стабильно **медленнее** по throughput (84–96% от Windows во всех потоках),
но **ловит заметно меньше хвостов**: `p999` на 8/16 потоках в WSL в 2–12 раз
ниже. Это ожидаемо: 1 MiB кольцо + `Backpressure::Drop` в обоих случаях, одинаковый
`ns_per_tick` и `threads`; разница — только стоимость TSC-фиксации и планировки
потоков ядра под WSL1 (KVM-граница). Для Drop-политики кастомное кольцо ticklog
держит стабильные p50≈15–18 нс в обеих средах, что согласуется с `README:13`-калибровкой.
